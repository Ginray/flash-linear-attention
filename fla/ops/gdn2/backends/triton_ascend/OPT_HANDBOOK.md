# 第一部分：GDN2 在算什么

## 1.1 从线性注意力说起

普通 Transformer 的注意力要把全部历史的 key 和 value 存下来，序列越长，内存和计算量都越大。线性注意力换了个思路：不存历史，只维护一个固定大小的矩阵 S（K 行 V 列）。每来一个新 token 就更新 S，然后从 S 里读出输出：

```
o_t = q_tᵀ · S_t
```

最简单的更新方式是直接累加：

```
S_t = S_{t-1} + k_t · v_tᵀ
```

这样计算量是每个 token 一步，但有个明显的毛病：所有写进去的信息都擦不掉。旧内容一直堆在 S 里，互相干扰，时间长了 S 就"糊"了。

## 1.2 Delta rule：写入之前先查一下旧的

DeltaNet 的改进是：写入的值不是 v 本身，而是"v 减去 S 里已经存着的关联值"。

先用当前的 key 去 S 里查一下，看这个 key 之前关联的是什么：

```
retrieve_t = k_tᵀ · S_{t-1}
```

然后写入差值：

```
S_t = S_{t-1} + k_t · (v_t − retrieve_t)ᵀ
    = S_{t-1} + k_t · (v_t − k_tᵀ S_{t-1})ᵀ
    = (I − k_t k_tᵀ) · S_{t-1} + k_t v_tᵀ
```

直觉是这样的：如果 k_t 在 S 里已经准确关联了 v_t，那查出来的东西和 v_t 一样，差值接近零，几乎不写；如果查出来的和 v_t 差很多，就把差值写进去。相当于"先删旧的、再写新的"，让 S 具备了覆写能力。

## 1.3 GDN2 是这个家族里最一般的版本

FLA 仓库里这条线的发展过程（[chunk.py](file:///home/syl/code/flash-linear-attention/fla/ops/gdn2/chunk.py) 开头的注释写得很清楚）：

```
线性注意力   只写不删
DeltaNet     加上 delta rule（写入前先检索修正）
GDN1         再加一个标量的遗忘门 g（旧状态先衰减再更新）
KDA          遗忘门 g 从标量变成 K 维向量（每个通道独立衰减）
GDN2         检索用的门 b 和写入用的门 w 都变成向量
```

chunk.py 的注释里写了退化关系：把 b 和 w 都设成同一个标量，GDN2 就变回 KDA；再把 g 压成标量，就变回 GDN1。所以 GDN2 是这一族里最一般的形式。

## 1.4 GDN2 的递推公式

完整的单步更新公式（[chunk.py:16-18](file:///home/syl/code/flash-linear-attention/fla/ops/gdn2/chunk.py#L16-L18)）：

```
S_t = (I − k_t (b_t ⊙ k_t)ᵀ) · Diag(exp(g_t)) · S_{t-1} + k_t (w_t ⊙ v_t)ᵀ
```

⊙ 表示逐元素相乘。四个部分各有各的用处：

| 部分 | 形状 | 干什么用的 |
|------|------|-----------|
| Diag(exp(g_t)) | K 维 | 衰减：旧状态按通道缩小。g 是负数，exp 之后在 0 到 1 之间 |
| b_t ⊙ k_t | K 维 | 检索时用的 key 按通道缩放，控制"查旧值"的力度 |
| I − k(b⊙k)ᵀ | K×K | 擦除投影：把查到的旧内容从 S 里扣掉（delta rule 的删旧半步） |
| w_t ⊙ v_t | V 维 | 写入的值按通道缩放，控制"写新值"的力度 |

注意两个门所在的轴不一样：b 在 key 这一侧（K 维），管的是删；w 在 value 这一侧（V 维），管的是写。这是 GDN2 论文的设计，两个门分别控制擦除和写入。

代码实现里 g 用的是对数域：先做累加和，要用的时候做减法得到"两个时刻的衰减比"。kernel 里到处看到的 `exp2(g_i − g_j)` 就是这个意思。为什么要这样做减法而不直接算 exp，后面 4.3 节会讲——直接算会数值溢出。

**参考实现**：[fused_recurrent.py](file:///home/syl/code/flash-linear-attention/fla/ops/gdn2/backends/triton_ascend/fused_recurrent.py) 就是把上面的公式逐个 token 翻译成代码（185 行到 232 行的主循环）：

```python
b_h *= exp(b_gk[:, None])                        # 旧状态先衰减
b_bk = b_b * b_k                                  # 检索用的 key = b ⊙ k
erase_d = tl.sum(b_h * b_bk[:, None], 0)          # 查旧值：(b⊙k)ᵀ S
b_v_new = b_w * b_v − erase_d                     # 要写入的差值
b_h += b_k[:, None] * b_v_new[None, :]            # S += k · 差值ᵀ
b_o = tl.sum(b_h * b_q[:, None], 0)               # 输出：qᵀ S
```

五行注释正好对应公式的五个步骤。这个 kernel 慢，但它就是公式本身，所以它是验证其他实现是否正确的对照物。

## 1.5 分块（chunked）：怎么把递推变成矩阵乘法

逐个 token 的循环没法并行，训练时太慢。分块算法把序列切成 64 个一组（BT=64），组内一次性用矩阵运算算完。推导过程不展开讲细节，只讲清楚结构，因为后面读 kernel 代码全靠这个结构。

**第一步：组内展开递推。** 把组内 64 步递推的衰减和擦除连乘展开。定义三个"吸收了门控"的新量：

- 带衰减的 key：k̃ = k ⊙ exp(g)（衰减吸收进 key）
- 带擦除门的 key：b̃ ⊙ k̃
- 带写入门的 value：ṽ = w ⊙ v（写入门吸收进 value）

展开之后，组内的状态变化可以整理成这个形式：

```
S_组尾 = S_组头 + Σ w_t u_tᵀ
```

其中 w 和 u 满足一个自洽方程（这就是 "WY 表示法" 的来源，wy_fast.py 文件名里的 wy 就是它）：

```
w = A⁻¹ · k̃
u = A⁻¹ · ṽ
A = I − K̃ B̃ᵀ     （组内的结构矩阵）
```

A 的第 (i,j) 个元素是 `δ_ij − k̃_iᵀ(b̃_j ⊙ k̃_j)`。A 是下三角的：

- 对角线是 1：自己的擦除投影只影响自己写入之前的东西
- 下三角 (i>j)：第 i 个 token 的擦除会删掉第 j 个 token（j 在它之前）写入的内容
- 上三角是 0：后面的写入不影响前面

前向算的 Aqk 和 Akk 就是 A 的组成部分（分别带 q 和带 b 的 key 的内积）。**前面出现"求逆"的原因就在这：要得到 w 和 u，必须算 A⁻¹。** diag_solve 和 inter_solve 两个 kernel 干的全部事情就是算 A⁻¹。

**第二步：组内再切小块。** 64 的一块再按 32 切（BC=32）。对角线上的小块（32×32 的三角矩阵）用前代替换（forward substitution，数值代数的标准方法）求逆；非对角的小块用 Schur 补公式合并。这里的块数 NC = BT/BC，是后面 Phase 4 优化的对象。

**第三步：跨组。** 组和组之间就是 `S ← S + w uᵀ` 的累加，这部分走的是和 KDA 共用的管线，不在 GDN2 专属的代码里。

## 1.6 前向的完整流程

[chunk_fwd.py](file:///home/syl/code/flash-linear-attention/fla/ops/gdn2/chunk_fwd.py) 按这个顺序调度：

| 步骤 | 算什么 | kernel | 在哪个文件 |
|------|--------|--------|-----------|
| 1 | 组内的衰减内积，得到 Aqk/Akk | sub_chunk | chunk_intra.py |
| 2 | 对角块求逆 + 非对角块合并（算 A⁻¹） | diag_solve、inter_solve_fused | chunk_intra.py |
| 3 | w = A⁻¹k̃，u = A⁻¹ṽ | recompute_w_u | wy_fast.py |
| 4 | 跨组状态递推和输出 | 和 KDA 共用 | 不在 GDN2 目录里 |

反向大致是这个流程倒过来：先从输出梯度 do 反推对 A 的梯度（chunk_bwd.py 里的五个 kernel），再经过 A⁻¹ 的转置传回 dq、dk、db、dg（chunk_intra.py 里的三个反向 kernel）。

## 1.7 反向要算哪些梯度

反向的梯度要穿过 A⁻¹，链式法则把计算分成两条路：

```
第一条路：do → dh → dv, dA          （chunk_bwd.py）
第二条路：dAqk/dAkk → dq, dk, db, dg （chunk_intra.py 的反向部分）
```

第二条路的核心公式（i 是目标行，j 是来源行，分对角、之前的块、之后的块三段求和）：

```
dq2[i,:] = Σ_j dAqk[i,j] · k̃[j,:] · 衰减比(i,j)
dk2[i,:] = Σ_j dAkk[i,j] · k̃[j,:] · 衰减比(i,j) ⊙ b_i
db[i,:]  = dk2 的对角部分[i,:] ⊙ k[i,:]
dg2[i,:] = q[i,:] ⊙ dq2[i,:] + (dk2 − dkt)[i,:] ⊙ k[i,:]
```

GDN1 和 KDA 没有 db 这一项（它们的 b 是标量或者不存在）。db 是 GDN2 反向多出来的一个完整的梯度张量，形状 [B,T,H,K]。第六部分的练习就是优化它的写入方式。

## 2.2 先把正确性测试跑通

改任何 kernel 之前，先跑验证脚本：

```bash

```

这个脚本有 22 个测试，覆盖前向、反向、变长序列、fp32/bf16/fp16、不整除的序列长度、初始状态传入等情况。对照组就是 1.4 节讲的 fused_recurrent——它慢，但显然正确。

## 2.3 了解代码是怎么接入的

适配不需要改任何调用方的代码。仓库用了一个 backend 注册机制（[__init__.py](file:///home/syl/code/flash-linear-attention/fla/ops/gdn2/backends/triton_ascend/__init__.py)）：

```python
class TritonAscendGDN2Backend(BaseBackend):
    @classmethod
    def is_available(cls) -> bool:
        from fla.utils import IS_NPU
        return IS_NPU                    # torch_npu 可用且当前设备是 NPU

    def chunk_gdn2_bwd_intra(self, *args, **kwargs):
        from ...chunk_intra import chunk_gdn2_bwd_intra_npu
        return chunk_gdn2_bwd_intra_npu(*args, **kwargs)

    def chunk_gdn2_bwd_intra_verifier(self, *args, **kwargs):
        return _verify_chunk(...)        # 检查输入确实是 NPU 上的张量，才接管
```

上层的函数带 `@dispatch` 装饰器，运行时根据设备选择用哪个 backend 的实现。想适配一个新的算子，要做的事情就是：在 backend 类里加一对方法（实现 + verifier），再写对应的 `xxx_npu` 函数。

# 第三部分：适配是怎么一步步做的

## 3.1 总体顺序

适配按数据流的顺序做，先做链路短的：

```
wy_fast（最上游、结构最简单）
→ 前向的 chunk_intra
→ 反向的 chunk_intra（最复杂，放在最后）
→ fused_recurrent
```

两条原则：

1. 每适配完一个 kernel 就跑相关的测试，不要攒到最后一起测。错误叠在一起就没法定位了。
2. 适配阶段写最简单、最直白的代码，哪怕用标量循环都行。目标是先把 22 个测试全部跑绿，把数值框架锁死。性能问题全部留到优化阶段。适配完时反向部分要 600 多微秒一步，很慢，但它是后面所有优化的对比基准。

## 3.2 第一步：公共的基础代码

写第一个 kernel 之前，先写好五样所有 kernel 都要用的东西。

**（1）按核数启动的循环结构**

CUDA 上写 Triton 是 `kernel[grid]`，一个 program 处理一个任务，任务数有多少 grid 就开多大。NPU 上这样做启动开销很大。改成：grid 只开核数个（这台机器是 24），kernel 内部用循环把任务消化掉：

```python
core_id = tl.program_id(0)
for task_id in tl.range(core_id, task_num, num_core):
    ...  # 每个核处理编号和自己余数相同的那些任务
```

任务数通常有几百个（K 的分块数 × 子块数 × 组数 × 头数），每个核会连续领到一串任务。任务编号怎么拆解（除法取余得到各个维度的下标）是纯标量运算，开销很小。

外面套一个启动函数，所有 kernel 共用：

```python
def _launch_bwd_intra_core_grid(kernel, *, task_num, kernel_kwargs):
    num_core = get_npu_properties()["num_aicore"]    # 24
    kernel[(num_core,)](num_core=num_core, task_num=task_num, **kernel_kwargs)
```

**（2）do_not_specialize 参数**

```python
@triton.jit(do_not_specialize=['B', 'T', 'NT', 'BH_TOTAL', 'task_num', 'num_core'])
```

不加这个参数的话，Triton 会按值来特化：T=1024 和 T=1030 会编译成两个不同的 kernel，各编译一次各缓存一份，编译时间翻倍。任务循环相关的标量参数都要加进去。

**（3）指针运算转成 int64**

```python
q_ptr = q + (bos * H + i_h).to(tl.int64) * K
```

`(bos*H + i_h)*K` 用 int32 算的话，张量元素总数超过 21 亿（2 的 31 次方）就会溢出。溢出不会报错，只会算出错误的地址，然后读到错的数据——小尺寸测试全对，大尺寸一跑就错。这种问题很隐蔽，所以测试脚本里必须放大尺寸的用例。

**（4）g 张量两种布局都支持**

上游传来的 g 可能是 [B,T,H,K] 也可能是转置过的 [B,H,T,K]（T 维连续）。CUDA 的实现要求固定布局，wrapper 里会强制 `contiguous()`，这一步转置要花 30 微秒左右。NPU 版做成编译期判断，两种布局走不同的地址计算，省掉这次转置：

```python
g_arg, g_t_contig = _gk_npu_arg(g, H)    # 探测实际布局
# kernel 里根据编译期常量选行跨度：
def _bwd_intra_g_row_stride(G_T_CONTIG, K, H):
    return K if G_T_CONTIG else H * K
```

**（5）变长序列的查表**

处理变长序列（varlen）时，kernel 里要先算"全局的组编号对应哪个序列的第几组"。这个映射预先在 host 侧算好存成表，kernel 里查表就行，不用做除法：

```python
i_n, i_t = tl.load(chunk_indices + i_t_o * 2), tl.load(chunk_indices + i_t_o * 2 + 1)
bos, eos = tl.load(cu_seqlens + i_n), tl.load(cu_seqlens + i_n + 1)
```

## 3.3 第二步：wy_fast——第一个 kernel

要算的东西（1.5 节的第三步）：`u = A·(w⊙v)`，`w = A·(k⊙b⊙e^g)`。A 已经由求逆那步算好了。kernel 主体就是两个循环，一个按 V 分块算 u，一个按 K 分块算 w：

```python
# value 侧：
b_vb = (b_v * b_wg).to(b_v.dtype)              # 写入门 w 在这里乘上
b_A  = tl.load(p_A, boundary_check=(0, 1))     # 注意：A 每个分块都要重新 load（原因见下）
b_u  = tl.dot(b_A, b_vb, allow_tf32=False)

# key 侧：
b_kb = b_k * b_b * exp2(b_gk)                  # 擦除门 b 在这里乘上
b_w  = tl.dot(b_A, b_kb, allow_tf32=False)
```

这里有两个 NPU 特有的问题，都是踩过坑才发现的：

**问题一：A 必须在循环里重新 load。** NPU 上 `tl.dot` 执行完之后，左操作数的内容会被破坏。如果像 CUDA 版那样把 A 提到循环外面 load 一次、循环里反复用，第二圈读到的是脏数据，精度测试会随机失败。代码里 175 行附近有注释记录这事。后面所有 kernel 只要一个 tile 要喂多个 dot，都要先复制一份再喂（常见写法是 `b_A + 0.0`）。

**问题二：衰减的基准点要选组的最后一行。** `k * exp2(g_last − g_i)` 把衰减统一换算到组尾。原因是这个结果（kg）是给跨组的状态递推用的，基准选在组的边界，传给下一组时衰减因子总是小于等于 1，不会溢出。

另外这个文件里还示范了 `@triton.heuristics` 的用法：调用方不需要输出 qg/kg 时，编译期就把存储代码裁掉，省一次写内存。

## 3.4 第三步：前向的 sub_chunk——标准形态

这个 kernel（chunk_intra.py 223 行起）是"直线代码 + 带掩码的 tl.dot"的典型形态，后面的 kernel 都照这个样子写。逐段看：

```python
# (a) 取基准行（组内中间那一行）：
p_gn = g + (i_ti + min(BC//2, T - i_ti - 1)).to(tl.int64) * H * K + tl.arange(0, BK)
b_gn = tl.load(p_gn, mask=tl.arange(0, BK) < K, other=0.0)[None, :]

# (b) 把衰减比拆成两个指数（为什么必须拆，见 4.3 节）：
b_gm = (b_g - b_gn).to(tl.float32)
b_gq = tl.where(m_c[:, None], exp2(b_gm), 0.)     # exp2(g_i − g_mid)
b_gk = tl.where(m_c[:, None], exp2(-b_gm), 0.)    # exp2(g_mid − g_j)

# (c) 转置要在 dot 之前做：
b_kgt = tl.trans(b_k * b_gk)

# (d) 两个 dot。GDN2 特有的 b 门乘在左边那个操作数上：
b_bk  = b_b * b_k
b_Aqk = tl.dot(b_q * b_gq, b_kgt, allow_tf32=False) * scale
b_Akk = tl.dot(b_bk * b_gq, b_kgt, allow_tf32=False)

# (e) 三角掩码在 dot 之后做：
m_Aqk = o_i[:, None] >= o_i[None, :]     # 下三角，含对角线
m_Akk = o_i[:, None] >  o_i[None, :]     # 严格下三角
b_Aqk = tl.where(m_Aqk, b_Aqk, 0.0)
b_Akk = tl.where(m_Akk, b_Akk, 0.0)
```

两个细节值得注意：

- **掩码为什么放在 dot 之后**：试过把掩码加在 dot 的输入上，BiSheng 编译器生成的代码会退化成很慢的路径。先算完再清零，多花一次 where 的开销，但保住了矩阵乘法的快路径。这个经验推广一下就是：NPU kernel 里能用事后清零解决的，就不要在读取或矩阵乘的输入上做条件判断。
- **输出的布局**：Aqk 存成 [T, BT]（整组宽度，后面合并阶段要用整行），Akk 只存 [T, BC]（对角块，求逆专用）。

## 3.5 第四步：求逆的两个 kernel

**diag_solve**：对角块是单位下三角矩阵（对角线是 1 的下三角），求逆用前代替换，一行一行地算。这里用的是纯标量的行循环（209 行到 218 行），看起来很原始，但 4.6 节会讲到：试过改成矩阵方法，全都更慢，这个 kernel 只能保持纯标量。循环次数是 `min(BC, T − i_ti)`，块尾被截断时少算几行。

**inter_solve_fused**：非对角块的合并，用 Schur 补公式。分成两块时核心就一行：

```python
b_Ai10 = -tl.dot(tl.dot(b_Ai11, b_Akk10), b_Ai00)
```

分三块、四块时是这条公式的级联展开（494 行到 533 行）。代码里有很多 `b_Ai11_c = b_Ai11 + 0.0`，看起来是废话，实际是必须的：同一个 tile 要喂给多个 dot 当左操作数，必须先复制，原因就是 3.3 节说的 dot 会破坏左操作数。

块的个数 NC 只支持到 4。因为合并逻辑是手工展开的编译期分支，块数再多代码量和寄存器压力都控制不住。BT=64、BC=32 时 NC=2，是主要场景。

## 3.6 第五步：反向（最难的部分，先用最笨的写法）

反向的数学在 1.7 节。适配时先写一个"一个大 kernel 算所有梯度"的版本：对角块用逐列的标量循环（照抄 KDA 的写法），之前的块用嵌套循环。正确，但一步要 600 多微秒。这就是优化的起点。

这个版本里埋着几个雷（编译器的问题、内存不够、数值溢出），在优化阶段全部炸了出来。但顺序是对的：先有一个测试全过的慢版本，再把它变快。

## 3.7 适配阶段的三个教训

1. **函数签名改动后要检查所有调用点。** 有一次改了 `_bwd_intra_g_row_stride` 的签名，有一个调用点忘了传参数，运行时才报错。之后养成习惯：改完签名先跑小尺寸的冒烟测试再跑全量。
2. **dot 破坏左操作数的问题无处不在。** wy_fast 里 A 的重新加载、inter_solve 里的 +0.0 复制、sub_chunk 里转置提前做——三个地方是同一个问题的三种表现。以后写新 kernel，第一个要检查的就是这个。
3. **适配阶段不要急着写好看的分块代码。** 朴素版本的价值是把数值问题先锁死。分块化是优化阶段的事，而且有专门的限制条件（4.1 节）。

# 第四部分：优化是怎么一步步做的

每一轮优化都走同样的流程：

```
用 profile 找到最慢的地方 → 猜测原因 → 先做小实验验证猜测
→ 改代码 → 跑 22 个测试 → 对比性能 → 记录结果
```

这个流程本身比任何单次优化的结果都重要，因为它是可以重复使用的。下面每个阶段都按这个流程展开。

## 4.1 第一次 profile：找到目标

```bash
python .agents/skills/fla-ascend-performance/scripts/profile_npu.py \
    /tmp/gdn2_bwd_workload.py --output-dir /tmp/npu_prof_bwd --with-stack
python .agents/skills/fla-ascend-performance/scripts/analyze_profile.py \
    /tmp/npu_prof_bwd --top-k 30
```

（workload 里的序列长度要让块数大于 1，比如 T=1024、BT=64、BC=32，块数就是 2。）

profile 显示：整体一步 2.69 毫秒，反向占 65%，前向占 35%。反向里最大的单个 kernel 是 `dq_db`，占总时间的 22.1%，它的标量指令占比 0.53——一半以上的时间花在标量运算上。

结论：先做反向，先做 dq_db，方向是把标量循环改成矩阵运算。

## 4.2 第一次尝试：改成分块写法，结果慢了 38 倍

这是整个项目最重要的一次失败。

**猜测**：dq_db 慢是因为逐列的标量循环，改成 3.4 节那种"掩码 + tl.dot"的写法应该能快很多。

**改动**：对角部分换成 dot，之前的块保持循环（循环里也用 dot）。

**结果**：22 个测试全过（说明算法是对的），但耗时从 7043 微秒涨到 271002 微秒，**慢了 38 倍**。

**排查过程**（这个过程比结论更值钱）：

1. 精度是对的，说明不是算错了，是生成的机器代码很糟糕；
2. 看代码结构：之前的块在"循环次数不确定的循环里"用 dot，对角块在"循环外面的直线代码里"用 dot——两种结构混在一起；
3. 找对照：同期用同样的方法改了另一个 kernel `dk_dg`，它的循环天然只有一次迭代（编译器能完全展开，等于纯直线代码），结果快了 2.16 倍。**同样的改法，一个快一个慢，唯一的区别就是有没有那个循环**；
4. 结论：BiSheng 编译器在"循环次数不确定的循环里有 tl.dot"和"循环外也有 tl.dot"同时出现时，生成的代码质量非常差。这是编译器的问题，不是算法的问题。

**这个结论后来变成了所有 kernel 的设计原则：一个 kernel 里要么全是循环，要么全是直线代码，不要混。** 它直接决定了后面 4.4 节的拆分方案，还在 4.8 节拦住了一次会倒退的改动。

## 4.3 第二次尝试：统一成循环，撞上两个新问题

**改动**：把对角块的计算也塞进循环里，用掩码控制最后一次迭代只算对角部分。这样所有 dot 都在循环里了。

**结果**：`dk_dg` 快了 2.16 倍；`dq_db` 还是慢。另外出了两个新问题。

**问题一：片上内存不够（UB 溢出）**

fp32 的大尺寸直接编译报错：

```
ub overflow, requires 2950144 bits while 1572864 bits available
```

UB（Unified Buffer）是 NPU 的片上共享内存，容量有限。tile 开太大、同时存活的 tile 太多就会超。解决思路是按公式估算而不是碰运气：

```
峰值内存 ≈ 系数 × BC × BK × 每元素字节数 ≤ 1572864 bits
```

实测这个 kernel 的峰值相当于 45 个 fp32 的 [BC,BK] tile，把选型系数从 10.5 调到 30.0，让选择函数自动把 BK 降到 32，编译通过。这套选型逻辑保留在 `_get_bwd_intra_bk`（chunk_intra.py 694 行）。反过来看，以后如果发现"tile 加大反而变慢"，第一个要怀疑的就是 UB 溢出。

**问题二：结果出现 NaN**

统一循环的版本测试全红，反向梯度里有 NaN。

调试方法是写一个单尺寸的复现脚本，一个测试一个测试地缩小范围，最后定位到：NaN 出现在对角三角块里列号大于行号的区域——正是被掩码清零的区域。

**原因**：衰减比是拿"首行"当基准拆成两个因子的。在三角块内部，列号大于行号时，`g_first − g_j` 是正数（g 沿序列单调递减，首行最大），`exp2(正的大数)` 算出 inf，然后掩码清零时 `inf × 0 = NaN`，NaN 会污染整个 tile 的 where 结果。

**修复：基准行改用块的中间一行**（chunk_intra.py 895 行）：

```python
i_mid = i_ti + tl.minimum(BC // 2, T_cur - i_ti - 1)   # 取中间行，注意别越界
b_e_neg = tl.where(m_t_valid, exp2(b_gm - b_g), 0.)
b_e_pos = tl.where(m_t_valid, exp2(b_g - b_gm), 0.)
```

**为什么取中间行就不会溢出**：g 单调递减时，两个因子的指数分别是 `g_mid − g_j` 和 `g_i − g_mid`。行和列都在块的范围内，而 mid 在正中间，所以两个指数的绝对值都不会超过半块的衰减量，有界。越界的行用 where 钳成 0，0 乘任何有限值都不会出 NaN。

**基准行的选择规律**（每处都要单独推一下指数的上界，没有万能公式）：

| 场景 | 基准点 | 原因 |
|------|--------|------|
| 对角块（行列都在块内） | 中间行 | 两个指数都被半块的量级限制住 |
| 之前的块（列的块在行的块之前） | 块的首行 | 列总在行前面，首行基准的指数总是负数 |
| 之后的块 | 目标块自己的行 | dkt_future kernel 用的方案 |
| wy 的 kg（要跨组传递） | 块的末行 | 接收方是下一组，基准放在组的边界 |

修复后 22 个测试全过。这次的体会：NaN 问题的排查成本远高于性能问题，指数上界这种东西推一次就要写进注释，别让下一个读代码的人再推一遍。

## 4.4 拆成两个 kernel：收益最大的一次（约 4 倍）

**背景**：统一循环的版本里，dq_db 还是最慢的 kernel（600 多微秒）。而 dk_dg 的成功说明：循环次数不确定这件事本身就是标量开销的主要来源。

**方案**：按代码结构（不是按输出）拆成两个 kernel：

```
dq_past     纯循环，只算"之前的块"          → 22.9 微秒/步
dq_db_diag  纯直线，只算对角块              → 52.6 微秒/步
```

两个加起来 75.5 微秒，对比统一版的 600 多微秒，**快了约 4 倍**。

拆分要配三个细节，缺一个都会出问题：

**（1）任务编号从 1 开始。** `i_k, i_i = i_kc // NC, i_kc % NC + 1`。编号为 0 的子块没有"之前的块"可算，让它从一开始就不进任务列表（任务数按 NK·(NC−1)·NT·BH 算），省掉 kernel 里的判断分支。

**（2）两个 kernel 用各自的 BK。** dq 系列内存系数 9.0，可以用 BK=64；dkt_future 内存系数 5.5，用 BK=32。之前所有 kernel 共用一个 BK，dq_db 被迫用的 32 传给了 dkt_future，导致它的任务数翻倍、耗时从 739 涨到 1424 微秒。分开选型之后 dkt_future 降到 39.1 微秒。

**（3）两个 kernel 的结果怎么合并。** 对角的 kernel 先写（直接覆盖），处理之前块的 kernel 读出来、加上自己算的、再写回去。同一个 stream 上顺序执行，先写后读有保证，不需要原子操作，也不需要额外的缓冲。只有 dkt_part 一个张量需要预先清零（因为"没有后面的块"时它得是 0，这个语义必须显式给）。

这一轮做完，22 个测试全过，反向的四个 kernel 加起来约 150 微秒一步。

## 4.5 前向换路径：降 24%，几乎没花力气

反向做完后，profile 里最大的 GDN2 kernel 变成了前向的 `intra_token_parallel`（102.9 微秒/步）。它是逐 token 的标量循环，每步只写 4 个元素，写内存的请求太碎，把写带宽打满了。

用 `git grep` 在仓库里搜了一下，发现已经有一个分块版本的 kernel `chunk_gdn2_fwd_kernel_intra_sub_chunk_npu`（就是 3.4 节讲的那个标准形态），只是被 `safe_gate` 参数的默认分支挡住了，一直没被用到。

同进程 A/B 对比：token_parallel 前向 1.00 毫秒，sub_chunk 0.88 毫秒；数值上输出差 6.1e-05（bf16 的精度水平），最终状态完全一致。

改动就是删掉 wrapper 里的分支，无条件走 sub_chunk。单 kernel 从 102.9 降到 78.7 微秒，**降 24%**。

教训：动手重写之前，先搜一下仓库里有没有现成的实现。一行 wrapper 的改动拿到 24%，是整个项目性价比最高的一次。

## 4.6 深挖 inter_solve：一次成功，两次失败

**背景**：`inter_solve_fused` 97.6 微秒/步，标量占比 0.497。原因是 BC=16 导致块数 NC=4，合并要 12 个 16×16 的小矩阵乘，加上求解链 9 个，小矩阵乘的效率很低。

**尝试一（失败）**：把每块的基准行统一成组的首行，能省 4 次 exp2 和 2 次转置。结果数值崩了——正是 4.3 节讲的那个问题：统一基准后列方向出现正指数，溢出成 NaN。每块用自己的基准行不是多余的，是数值稳定的必要结构。回滚。

**尝试二（成功）：BC 从 16 改到 32，块数从 4 降到 2。** 矩阵乘的数量从 12+9 降到 4+1：

```python
BC = min(_FWD_BC, BT // 2)    # BT=64 时 BC=32；BT=32 时保持 16，块数仍是 2
```

UB 预算按新的 BC 重算。inter_solve 从 97.6 降到 **58.9 微秒（降 40%）**；diag_solve 从 23.8 涨到 61.1 微秒（它的标量循环次数和 BC 的平方成正比，翻倍是预期内的）。整体前向端到端**降 11%**。

这里有个测量上的教训：一开始用跨进程的对比测试，读出来的结果是"没有变化"；改成同一个进程里交替跑两个版本（各跑 3 轮、每轮 30 次取最小值和中位数），才看出 11% 的差距。**多人共享的 NPU 上，跨进程的耗时数据不可比，结论必须用同进程交替对比来确认。**

**尝试三（失败两次）：diag_solve 改成分块求逆。** 数学上完全成立（把 32×32 的三角矩阵拆成四个 16×16，对角两个直接求逆，反对角块用公式算），标量循环的次数还能少一点。两种写法都试了：按实际尺寸算循环次数的版本从 61 涨到 110.5 微秒；固定循环次数加掩码的版本 117.2 微秒。全都是 4.2 节那个编译器问题——只要循环和 dot 混在一个 kernel 里，不管循环次数怎么算、dot 在循环里还是循环外，生成的代码都很差。结论：这个 kernel 只能保持纯标量。代码里留了注释；如果将来编译器修好了这个问题，改回分块求逆能把它降回 28 微秒左右。

顺手做的清理：删掉了启动函数里的 `num_warps=2`。NPU 不支持这个参数（传了也被忽略），是移植时从 CUDA 代码带过来的习惯。

## 4.7 sub_chunk 的消融实验：确认这个 kernel 到头了

**方法**：对 sub_chunk 做了 10 组对照实验，每组只改一个变量，在同进程里量耗时。几个有代表性的结果：

| 改动 | 结果 |
|------|------|
| 去掉两个 dot（只测开销，结果不对） | 耗时少了一半——dot 本身占 kernel 约 53%，是实打实的计算量 |
| exp2 从 3 次减到 1 次 | 没变化，exp2 不是瓶颈 |
| gate 因子从 fp32 降到 bf16 | 快 23%，但这改变了中间计算精度，属于要发 RFC 讨论的设计变更，先记录不实施 |
| 两个小 dot 合成一个大 dot | 更慢 |
| 两个 dot 合成一个（列拼接） | 能快 5%，但拼接的写法 BiSheng 编译不过 |
| 改成常驻循环（kernel 不退出，自己领任务） | 慢 20%，又是 4.2 节的编译器问题 |

**结论**：这个 kernel 的时间一半是 dot 的真实计算量，一半是 gate 因子的生成链，所有结构上的改法要么更慢要么编译不过。**它已经到了编译器允许的上限，不再投入。**

消融实验的价值在这个例子里体现得很清楚：没有这些对照，"到头了"只是感觉；有了它们，每条路的"为什么不行"都有数据。

## 4.8 融合两个 kernel + 验证一个猜测

**融合**：`dq_db_diag`（52.6 微秒）和 `dk_dg`（55.7 微秒）读的输入完全一样，任务划分也一样，而且后者的输出就是前者的输入更新——中间结果在显存里走了一个来回。把两个合成一个：

合成之前先在纸上把公式重新排了一遍，确保逐项对得上（这个步骤不能省，两个 kernel 的公式各自变过形，直接拼会错）：

```
原来：diag 算出 dq2/dk2/db/dg2 → 存显存 → dk_dg 读回来加上 dkt 项再存
融合后：dk2 = (diag_dk + dk_in + dkt) + past·b
        dg2 = q·dq2_diag + (diag_dk − dkt)·k + dg_in + q·past + (past·b)·k
```

实现时注意两条：转置全部放在 dot 之前；共享的 tile 喂多个 dot 之前先复制。结果从 213.9 降到约 205 微秒，降 3~5%。

**低于预期的原因**：这个 kernel 标量占比 0.5，大头是标量开销不是访存，融合省掉的只是中间量的一次读写。得到的经验：**融合之前先估算中间量的读写占 kernel 耗时的比例，想清楚收益上限再动手。**

**验证一个猜测**：profile 里看到 boundary_check（边界检查）到处都是，猜测它是标量开销的来源之一。写了个 20 行的小测试，三个版本对比：带边界检查 41.1 微秒，去掉检查改用 where 42.0，全去掉 41.3——没有差别，猜测被推翻。顺带测了 exp2：去掉之后 39.4 对 41.7，只占 6%，也不值得动。

这个例子是想说明流程里"先做小实验"这一步的意义：二十行代码十分钟，就能避免一次没用的改动。

# 第五部分：经验总结

## 5.1 每轮优化的固定流程

```
profile 定位 → 提出猜测 → 小实验验证 → 改代码 → 跑测试 → 对比性能 → 记录
```

几个要点：

- **先看结构再看细节。** 先弄清整体时间花在前向还是反向、哪个 kernel 最大、指标是什么类型，再决定动哪里。跳过这一步直接抠指令，很容易在一个占 2% 的 kernel 上耗一下午。
- **猜测要具体到能验证。** "boundary_check 是标量开销的来源"可以被二十行代码验证或推翻；"这个 kernel 有点慢"验证不了什么。
- **小实验优先于改代码。** 微基准或消融实验十分钟出结果；直接改 kernel 再 profile，一小时起步，还容易得出错误结论。
- **测试每次全量跑。** 22 个测试跑一遍也就几分钟，红了立刻回滚，不要带着红的测试继续开发。
- **失败也要记录。** 38 倍的倒退、两次失败的求逆改法、被推翻的猜测——这些记录划定了"什么路走不通"，下次不会重复踩。

## 5.2 指标怎么看（对照表）

| profile 里的特征 | 说明什么 | 该做什么 | 例子 |
|------------------|---------|---------|------|
| 标量占比 > 0.4 | 时间花在标量指令上 | 把标量循环改成矩阵运算，或拆 kernel | 4.2 / 4.4 节 |
| 向量占比很低 | 已经是逐元素运算的形态，没多少可压的 | 考虑到此为止 | 4.7 节 |
| 搬数据的占比高、计算的占比低 | 受访存限制 | 合并 kernel 减少中间量 | 4.8 节 |
| 榜单里有 Transpose/Copy 这类框架操作 | 问题在 wrapper 不在 kernel | 改输出的写入布局 | 第六部分练习 |
| 任务数少于核数 | 核没吃满 | 先查是不是编译器限制，再想怎么拆 | 4.2 节 |

## 5.3 性能测量的三条规矩

1. 结论必须来自**同进程交替对比**，或者**两次独立的 profile 方向一致**；
2. 单次测量只当参考，不当结论；
3. 收益幅度小于噪声范围（整体耗时 ±9%）的不算数。

实际例子：有个改动第一次 profile 显示"整体快 10%"，复测后发现是噪声；BC 从 16 改 32 那次，跨进程测试显示"没变化"，同进程交替对比才显出 11% 的差距。

## 5.4 常用的优化手段

| 手段 | 什么时候用 | 例子 | 收益 |
|------|-----------|------|------|
| 改输出布局，直接写到最终位置 | 榜单里出现框架的转置/拷贝操作 | 第六部分练习 | 预计每步省 70~80 微秒 |
| 拆 kernel | 标量占比高 + 循环和直线代码混在一起 | 4.4 节 | 约 4 倍 |
| 合 kernel | 两个 kernel 读一样的输入、有中间量走显存 | 4.8 节 | 3~5% |
| 标量循环改成矩阵运算 | 标量占比高 + 有现成的分块写法 | 4.2 / 4.5 节 | 24%（先搜仓库！） |
| 换指数的基准行 | 结果出现 NaN | 4.3 节 | 前置条件 |
| 按 UB 预算选 tile 大小 | 编译报 ub overflow，或 tile 变大反而慢 | 4.3 节 | 前置条件 |

## 5.5 什么时候算做完了

满足任何一条就可以停：① GDN2 自己的 kernel 里没有"占比超 5% 且结构上还能动"的目标了；② 剩下的大头是和 KDA 共用的管线，或者是编译器的限制；③ 连续两个猜测被实验推翻。

停下来不等于放弃：没做的优化项，连同方案、预期收益、风险、已经验证走不通的路，都写进 OPT_LOG.md 的 Phase 7 计划里，下次接着做。

# 第六部分：动手练习（db2 的写入布局优化）

这是当前计划里的下一个优化项（Phase 7a），也是最适合上手的一个：改动范围小、验证步骤完整、预期收益比之前任何一次 kernel 内部的优化都大。

**现状**：反向的 wrapper 结尾（chunk_intra.py 1165 行附近）是这样的：

```python
db2_combined = db2.permute(1,2,3,0,4).contiguous().reshape(B,T,H,NK*BK)[..., :K]
db = db.add_(db2_combined)
```

两个 kernel 写 db 时用的布局是 [NK, B, T, H, BK]（K 的分块编号在最外面），收集起来要整块地转置加拷贝。profile 实测这些框架操作的开销：转置 54~64 微秒 + 拷贝 8 微秒 + 加法 6 微秒，**加起来每步 70~80 微秒**，占反向这条链路的 15%。

**任务**：让两个写 db 的 kernel 直接按 [B,T,H,K] 的布局写，wrapper 只留一次加法。

按第五部分的流程走：

**第一步，确认问题。** 自己 profile 一次反向，在 top 30 的列表里找到那三个框架操作，记下数值。（练习 5.2 节的查表方法。）

**第二步，改 kernel。** 涉及 diag_fused 里的 `db_ptr` 和 `p_db`（927 行、975 行附近），以及 dq_past 里的对应两处（810 行、844 行附近）。把块指针换成和 dkt_part 一样的写法：

```python
db_ptr = db + (bos * H + i_h).to(tl.int64) * K          # [B,T,H,K] 布局的基地址
p_db = tl.make_block_ptr(db_ptr, (T_cur, K), (H * K, 1),
                         (i_ti, i_k * BK), (BC, BK), (1, 0))
```

**第三步，改 wrapper。** `db2 = q.new_empty(B, T, H, K, dtype=torch.float32)`，删掉 permute 那两行，改成 `db = db.add_(db2)`。

**第四步，验证。** 跑 22 个测试 → 同进程 A/B（对比整体耗时和两个 kernel 各自的耗时）→ 再 profile 一次确认那三个框架操作从榜单上消失了 → 把数据记进 OPT_LOG.md。

**动手之前先想清楚两个问题**（答案都是"是"，但要想明白为什么）：

1. K 方向的 NK 个分块各写自己的列区间 [i_k·BK, (i_k+1)·BK)，互相会不会重叠？
2. 对角 kernel 先写、之前的块的 kernel 读改写，这个先后顺序在同一个 stream 上还能保证吗？

# 附录：NPU 上踩过的坑（速查）

| 症状 | 原因 | 怎么处理 |
|------|------|---------|
| 改完 dot 之后耗时暴涨（38 倍 / 20% / 81%） | 循环次数不确定的循环里有 tl.dot，或者循环外还有 dot | 把循环部分和直线部分拆成两个 kernel（4.2 / 4.4 / 4.6 / 4.7 节） |
| 融合后的 kernel 精度随机失败 | tl.dot 会破坏左操作数的内容 | 转置提前做；共享的 tile 先复制再喂；循环里每次重新 load（3.3 / 4.8 节） |
| 结果里有 NaN（测试红，位置在三角掩码区） | 指数基准选错，出现正的大指数，inf 乘 0 变 NaN | 换基准行（对角块用中间行），越界的行钳成 0（4.3 / 4.6 节） |
| 编译报 `ub overflow` | tile 太大，片上内存不够 | 按公式选 BK（4.3 节） |
| `[64,32]` 形状的存储编译报错 | 编译器对这个形状的内存布局有 bug | 避开这个形状，改之前先用小程序试编译 |
| `libdevice.exp2` 编译失败 | Triton-Ascend 3.2.0 不支持 libdevice 函数 | 用 `tl.exp2`（实测 exp2 只占 6%，不影响大局） |
| `h_kernel.cache.clear()` 报 AttributeError | Heuristics 包装类把里面的 autotuner 藏起来了 | `tuner = h_kernel.fn if hasattr(h_kernel, 'fn') else h_kernel` 再 clear |
| profile 的耗时和实际测量对不上 | 采集了多步数据取了总和 | 确认采集了几步，再除 |
| 跨进程测出来"没变化" | 共享设备被别人占用，数据漂移 | 同进程交替对比（4.6 节） |
| dot 的输入加了掩码之后变慢 | 编译器生成了低效路径 | 先算完再用 where 清零（3.4 节） |
